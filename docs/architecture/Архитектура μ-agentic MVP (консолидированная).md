# Архитектура μ-agentic MVP (консолидированная)

## 1. Назначение

Агент оплачивает покупки, никогда не видя платёжных реквизитов; владелец задаёт правила и видит полный журнал решений. Один сценарий: подписка/цифровая покупка через Stripe.

## 2. Общая схема

```
                    ┌─────────────── μ-объект (CBOR/COSE) ───────────────┐
                    │ 1.Core  2.Ω-слот  3.Δ-слот  4.Value-слот  5.Log    │
                    └────────────────────────────────────────────────────┘
                                          ▲ читает/пишет атомарно
┌───────┐  POST /intent   ┌──────────────┴──────────────┐   PaymentIntent  ┌────────┐
│ Agent │ ──────────────► │        Runtime (демон)      │ ───────────────► │ Stripe │
└───────┘  подпись agent  │ Ω-check → Δ-check → исполн. │    TLS 1.3       └────────┘
                          └──────┬───────────────┬──────┘
                                 ▼               ▼
                          Биометрия ОС      Enclave (токен)
                          (порог Δ)         L0-якорь
```

## 3. μ-объект — структура

| Слот     | Поля                                                                         | Изменяемость                                  |
| -------- | ---------------------------------------------------------------------------- | --------------------------------------------- |
| 1. Core  | ID (UUID v7), owner_pubkey, created_at, version, checksum SHA-256            | При выпуске                                   |
| 2. Ω     | operations:["payment"], connectors:["stripe"], merchant_classes, max_ceiling | Только перевыпуск μ с новой подписью          |
| 3. Δ     | daily_limit, merchant_whitelist, confirm_threshold                           | Владельцем в любой момент (подпись владельца) |
| 4. Value | token_ref (указатель в enclave), connector_id, currency                      | При привязке источника                        |
| 5. Log   | hash-chain: intent → решение Ω/Δ → результат/отказ                           | Append-only                                   |

Формат: CBOR (RFC 8949), подпись COSE ES256 (RFC 9052). Секретов внутри μ нет. Размер: 0.3–3 КБ (наследие ЭО).

## 4. Стек

| Уровень        | Реализация                                                                                                      |
| -------------- | --------------------------------------------------------------------------------------------------------------- |
| L0 Якорь       | Secure Enclave / StrongBox / TPM 2.0; ключ μ и Payment Token — non-exportable                                   |
| L1 Формат      | CBOR + COSE + SHA-256                                                                                           |
| L2 Крипто      | Только ECDSA P-256 (ES256), ключи в железе                                                                      |
| L3 Runtime     | Локальный демон (Rust или Node/TS); атомарные операции над μ                                                    |
| L4 Политики    | Плоский JSON, 3 правила Δ + статичный Ω-фильтр (~30 строк кода)                                                 |
| L5 Исполнение  | Stripe: PaymentIntent + сохранённый Payment Method Token + idempotency key                                      |
| L6 Вход агента | localhost REST `POST /intent {merchant, amount, purpose, agent_id}` + подпись ключом агента + allowlist агентов |
| L7 Человек     | Системная биометрия ОС (LocalAuthentication / BiometricPrompt) при сумме > confirm_threshold; просмотр Log      |

## 5. Поток исполнения (попунктно)

1. Агент шлёт подписанный intent на localhost.
2. Runtime проверяет подпись агента и allowlist.
3. **Ω-check:** операция payment? коннектор stripe? класс мерчанта допустим? сумма ≤ max_ceiling? Нет → отказ, запись в Log.
4. **Δ-check:** дневной лимит не исчерпан? мерчант в whitelist? Сумма > confirm_threshold → биометрия владельца.
5. Runtime берёт token_ref → enclave отдаёт операцию с токеном → Stripe PaymentIntent (idempotency key = hash intent).
6. Результат (успех/ошибка) → запись в Log-цепочку → ответ агенту (без каких-либо реквизитов).

## 6. Модель угроз (MVP-уровень)

| Угроза                             | Контрмера                                                        |
| ---------------------------------- | ---------------------------------------------------------------- |
| Агент извлекает реквизиты          | Токен только в enclave; ответы агенту не содержат payment-данных |
| Подмена Δ (завышение лимита)       | Δ подписывается ключом владельца; checksum μ                     |
| Пробитие потолка через Δ           | Ω-ceiling неизменяем без перевыпуска μ                           |
| Повторное списание                 | Stripe idempotency keys                                          |
| Копирование μ на другое устройство | Ключи non-exportable → копия не подписывает                      |
| Ложный агент                       | Allowlist + подпись запроса                                      |

## 7. Зависимости и границы

* Внешние: CBOR-lib, Stripe SDK, keystore API платформы — **3 шт.**
* Вне MVP (места зарезервированы): MCP-адаптер поверх REST, мультиконнекторы, Cedar, профили Ω, MPC-бэкап Vault, mTLS для облачных агентов, офлайн/P2P (вариант 2 на том же формате L1).

## 8. Критический путь до старта

1. Юридическая проверка: доступ к network tokens / Stripe token requestor (партнёрское ограничение, не техническое).
2. Прототип L1+L4 (объект + правила) — без денег, mock-коннектор.
3. Sandbox Stripe → первый живой цикл п.5.
4. Тест-фраза приёмки: «агент купил подписку за 20 €, не увидев ни карты, ни ключей; владелец видит в журнале кто/что/почему».
