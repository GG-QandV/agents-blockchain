# Архитектура μ-agentic MVP v3 (полная, crypto-first)

---

# РАЗДЕЛ 1. АРХИТЕКТУРА

## 1.1. Назначение

Агент оплачивает покупки в крипто-принимающих сервисах, никогда не имея доступа к ключам кошелька; владелец задаёт правила (Δ) в пределах неизменяемого потолка (Ω) и видит полный журнал решений. Банки/карты — заглушки на едином интерфейсе коннектора.

## 1.2. Общая схема

```
                ┌───────────────── μ-объект (CBOR/COSE) ─────────────────┐
                │ 1.Core  2.Ω  3.Δ  4.Value(key_ref)  5.Log(WAL+chain)   │
                └─────────────────────────────────────────────────────────┘
                                       ▲ атомарно, однопоточно
┌───────┐  unix socket   ┌────────────┴────────────────┐   signed tx    ┌──────────────┐
│ Agent │ ─────────────► │ Runtime: очередь intent'ов  │ ─────────────► │ RPC ×2 → L2  │
└───────┘  подпись       │ Ω → Δ(reserve) → WAL → exec │                │ (USDC/Base)  │
                         └───┬──────────┬──────────┬───┘                └──────────────┘
                             ▼          ▼          ▼
                       Биометрия   Enclave     bank_stub / card_stub
                       (TTL 15м)   (ключи)     (SIMULATED → Log)
```

## 1.3. μ-объект — 5 слотов

| Слот     | Поля                                                                                                                                     | Изменяемость                         |
| -------- | ---------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------ |
| 1. Core  | ID (UUID v7), owner_pubkey, created_at, version, checksum SHA-256                                                                        | При выпуске                          |
| 2. Ω     | operations:["payment"], connectors:["crypto","bank_stub","card_stub"], max_ceiling (в валюте актива), merchant_classes — зарезервировано | Только перевыпуск μ с новой подписью |
| 3. Δ     | daily_limit (скользящее окно 24 ч), whitelist адресов получателей (0x…), confirm_threshold                                               | Владельцем, подпись владельца        |
| 4. Value | key_ref (ключ кошелька под enclave-защитой), address, chain_id, asset (USDC), connector_id                                               | При привязке источника               |
| 5. Log   | WAL + hash-chain: PENDING → SETTLED/FAILED; intent, решения Ω/Δ, tx_hash, gas                                                            | Append-only                          |

Секреты в μ не хранятся. Размер объекта 0.3–3 КБ (наследие ЭО). Формат общий с будущим вариантом 2 (P2P/ЭО).

## 1.4. Поток исполнения

1. Intent `{recipient, amount, purpose, agent_id}` через unix socket → проверка подписи агента + allowlist.
2. **Ω-check:** операция payment, коннектор существует, amount+gas_estimate ≤ ceiling. Отказ → Log.
3. **Δ-check с резервированием:** окно 24 ч по timestamp'ам Log; получатель в whitelist адресов; > threshold → биометрия владельца (TTL 15 мин → авто-отказ).
4. **WAL:** запись PENDING (intent, решения, nonce цепи) до исполнения.
5. Enclave отдаёт ключ → подпись транзакции в памяти демона → отправка через 2 RPC → ожидание финальности.
6. Log: SETTLED (tx_hash) / FAILED (+откат резерва). Агенту — только статус, никогда ключи/адреса источника.
7. Рестарт демона → сверка PENDING с цепью (по nonce/tx_hash) до приёма новых intent'ов.

## 1.5. Модель угроз

| Угроза                                | Контрмера                                                            |
| ------------------------------------- | -------------------------------------------------------------------- |
| Агент извлекает ключ                  | Ключ в enclave-обёртке; ответы без секретов; подпись — внутри демона |
| Подмена Δ / пробитие потолка          | Подпись владельца на Δ; Ω неизменяем без перевыпуска; checksum μ     |
| Параллельные intent'ы пробивают лимит | Однопоточная очередь + check-and-reserve                             |
| Двойная отправка                      | Нативный nonce аккаунта в цепи                                       |
| Крэш между отправкой и учётом         | WAL + сверка с цепью при старте                                      |
| Подмена получателя                    | Whitelist по криптоадресу — неподделываем                            |
| Локальный процесс-самозванец          | Unix socket с правами ОС + подпись + allowlist                       |
| Перевод системных часов               | Окно лимита по Log-timestamp'ам                                      |
| Компрометация RPC                     | 2 независимых провайдера, сверка nonce/баланса                       |
| Копия μ на другом устройстве          | Enclave-ключи non-exportable → копия не работает                     |

## 1.6. Явные ограничения (проговариваются владельцу)

1. purpose не контролируется — только получатель и сумма.
2. Транзакции необратимы → confirm_threshold ставить низко.
3. Потеря устройства = потеря ключа кошелька и журнала; держать на μ операционные суммы. MPC-бэкап — фаза 2.
4. В момент подписи ключ находится в RAM демона (ограничение кривых enclave).
5. bank/card коннекторы — симуляция (SIMULATED в Log).

## 1.7. Вне MVP (места зарезервированы)

MCP-адаптер поверх REST • живые bank (Pay-by-Bank/PSD2/Interac) и card (network tokens) коннекторы • Cedar-политики • профили Ω • MPC-бэкап Vault • мультивалюта+оракул • mTLS для облачных агентов • x402-протокол приёма • вариант 2 (P2P/офлайн ЭО) на том же L1-формате.

# РАЗДЕЛ 2. СТЕК + ПРОТОКОЛЫ/ТЕХНОЛОГИИ

## 2.1. Уровни

| Ур. | Компонент        | Технология                                                                                                              | Протокол/стандарт                                                                                  |
| --- | ---------------- | ----------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| L0  | Аппаратный якорь | Secure Enclave (iOS) / StrongBox Keystore (Android) / TPM 2.0 (ПК)                                                      | Ключ подписи μ: P-256 non-exportable; ключ кошелька: AES-wrap enclave-ключом                       |
| L1  | Формат μ         | Сериализация + подпись контейнера                                                                                       | CBOR (RFC 8949), COSE ES256 (RFC 9052), SHA-256                                                    |
| L2  | Криптослой       | Подпись μ/лога: ECDSA P-256 (в железе); подпись транзакций: secp256k1 (EVM) в памяти демона                             | RFC 6979 (детерминированный ECDSA), EIP-155 (защита от cross-chain replay), EIP-1559 (модель газа) |
| L3  | Runtime          | Демон: Rust (памятебезопасность) или Node/TS; однопоточная очередь; атомарный check-and-reserve                         | Файловая атомарность: write-temp + fsync + rename                                                  |
| L4  | Политики Ω/Δ     | Плоский JSON + ~30 строк кода проверки; окно 24 ч по Log-timestamp'ам                                                   | JSON Schema для валидации структуры                                                                |
| L5  | Исполнение       | Chain: Base или Arbitrum (L2 Ethereum); актив: USDC; библиотека: ethers.js/viem (TS) или alloy (Rust); 2 RPC-провайдера | ERC-20 transfer, JSON-RPC (eth_sendRawTransaction, eth_getTransactionReceipt), финальность L2      |
| L5s | Заглушки         | bank_stub, card_stub — единый trait/интерфейс Connector: quote/execute/status                                           | Возврат SIMULATED, полный цикл в Log                                                               |
| L6  | Вход агента      | Unix domain socket (права ОС) / named pipe (Windows)                                                                    | JSON-запрос + подпись Ed25519 ключом агента + allowlist pubkeys                                    |
| L7  | Человек          | Системная биометрия: LocalAuthentication (iOS/macOS) / BiometricPrompt (Android) / Windows Hello                        | Подтверждение > threshold; TTL 15 мин                                                              |

## 2.2. Протоколы по потокам

| Поток           | Протокол                                                                    |
| --------------- | --------------------------------------------------------------------------- |
| Агент → μ       | JSON over unix socket, подпись запроса                                      |
| μ → сеть        | HTTPS/TLS 1.3 → JSON-RPC ноды ×2                                            |
| μ → владелец    | Биометрический системный диалог                                             |
| Внутри μ        | Log = hash-chain (каждая запись хеширует предыдущую); WAL перед исполнением |
| Идемпотентность | Nonce аккаунта цепи (протокольная гарантия)                                 |

## 2.3. Зависимости (4)

1. CBOR/COSE-библиотека
2. EVM-библиотека подписи (viem / alloy)
3. Keystore API платформы
4. RPC-провайдеры (Alchemy/Infura/QuickNode — 2 из 3, взаимозаменяемы)

## 2.4. Критический путь

1. Прототип L1+L4: μ-объект + правила + mock-коннектор (без сети).
2. Крипто-коннектор на testnet (Base Sepolia).
3. Живой цикл на mainnet с микро-суммами.
4. Тест-фраза приёмки: «агент оплатил API-сервис 5 USDC, не увидев ключа; владелец видит в журнале кто/что/почему/tx_hash; bank_stub прогоняет тот же поток в SIMULATED».
